# 2026-07-27 GenAI Generation Agents — 100% Production Abstain — Incident Report

**Status: MITIGATED, NOT RESOLVED.** The two broken student-facing surfaces are disabled and no longer serve a dead end. The underlying defects that made them dead ends are still unfixed. A related, older defect (`ncert-solver`) surfaced by this incident is also still unfixed. See "Outstanding / NOT resolved" below before reading this as a closed incident.

## Summary

- **Detection (stage 1) date:** 2026-07-24, same day as launch. Per PR #1393: *"After the GenAI flags were enabled in production, the CEO reported seeing no difference in the app."* This caught fault A (built but unreachable).
- **Detection (stage 2) date:** 2026-07-27. Per PR #1394: *"A post-merge audit of #1393 found that the Study Tools features it shipped **abstain 100% of the time in production and cannot ever succeed**."* This caught fault B (reachable but non-functional) — found only *because* fault A had just been fixed and the surface became reachable enough to audit.
- **Scope:** Two of three brand-new GenAI agents shipped 2026-07-24 — Lesson Generation (`ff_lesson_generation_v1`) and Content Generation (`ff_content_generation_v1`). The third (Outcome Prediction) was never wired to any UI and so was never reachable at all (separate, still-open issue — see Outstanding item (c)).
- **Earliest known regression:** Not precisely established. The proximate incident (these two agents shipping broken) starts 2026-07-24. The underlying defect they exposed — the strict-mode `rag_status='ready'` coverage gate having zero satisfiable production rows — predates that: PR #1394 discloses that the pre-existing `ncert-solver` Edge Function has been hitting the identical dead end "for months," undetected. No exact onset date could be established from source alone (no production trace history was queried in this investigation — see "Could not verify" in the reporting note at the end).
- **Customer impact:** Fail-safe, not fail-unsafe — the defect produces a calm bilingual "not ready yet" abstain message with suggested alternative chapters, never a crash, wrong answer, or data-integrity fault. Real impact window is narrower than the full "100/07-24 to 07-27" span: the two agents were flag-enabled but had **zero UI caller** until PR #1393 shipped the morning of 2026-07-25, so the only window in which a real student could reach either endpoint through the product (as opposed to a direct authenticated HTTP call) is **2026-07-25 through 2026-07-27** (roughly two days). Within that window, an unknown number of students who opened `/foxy`, selected a chapter, and tapped the new "Diagram" or "Lesson notes" pills received the abstain envelope on effectively every attempt. Exact affected-student count could not be verified (no analytics/telemetry query was available in this investigation).
- **Resolution date:** None — see status line above. Both flags were forced OFF on **2026-07-27** (mitigation, not resolution).

## Root cause (three linked faults, one still-live side-finding)

**Fault A — shipped with no way to reach it (2026-07-24).** PRs #1389 (`370e488a`, Outcome Prediction, `apps/host/src/app/api/predict/outcome/route.ts`), #1390 (`bf917708`, Lesson Generation, `apps/host/src/app/api/lesson/route.ts`), and #1391 (`265251a7`, Content Generation, `apps/host/src/app/api/content/diagram/route.ts`) all merged 2026-07-24, each behind its own default-OFF flag. PR #1392 (`71b65689`, same day) then activated flags: `ff_response_eval_v1` → 100%, `ff_lesson_generation_v1` / `ff_content_generation_v1` → 10% canary. Hours later, per CEO decision, production was flipped by hand via the super-admin console straight to 100% for both — the migration that codifies this (`supabase/migrations/20260724220000_set_ff_generation_rollout_100.sql`) documents *"On 2026-07-24 the CEO decided to go straight to FULL rollout... Production was flipped to 100% by hand via the super-admin feature-flag console at that time."* (That migration file itself was only committed to git the next morning, as part of PR #1393, specifically because the two already-merged-but-unapplied 10%-canary migrations would otherwise have silently downgraded the live 100% state on the next `supabase db push` — the file's own header calls this out.) Per PR #1393's own description: phases 1 through 5c of the whole GenAI ecosystem build (Model Gateway, Unified Memory, Agent Registry, ResponseEval, plus the three Phase-5 agents) shipped **88 files / 15,433 insertions with zero `.tsx` files** — none of the three new agent endpoints had any caller anywhere in the web or Flutter app. Enabling the flags "made unreachable endpoints return 200 instead of 403 to students who had no way to call them."

**Fault B — reachable, but abstains on ~100% of real requests (found 2026-07-27).** PR #1393 (`1365a3da`, merged 2026-07-25) built the missing front door — `apps/host/src/app/foxy/_hooks/useGenAiContentFlags.ts` and `apps/host/src/app/foxy/_components/StudyToolsBar.tsx` — for two of the three agents (Lesson, Content; **not** Outcome Prediction). The post-merge audit of that PR found both newly-reachable agents fail every real request. Root cause, verified directly in source:
  - Both generators build their `GroundedRequest` with `mode: 'strict'` (confirmed in source: `packages/lib/src/lesson/generate-lesson.ts:260`, `packages/lib/src/diagram/generate-diagram.ts:298`).
  - Strict mode runs a coverage precheck (`supabase/functions/grounded-answer/coverage.ts`) before any Voyage/Claude call, inside `runPipeline()` in `supabase/functions/grounded-answer/pipeline.ts`. It is a hard gate: `checkCoverage()` returns `ready:false` — short-circuiting straight to `abstain_reason: 'chapter_not_ready'` — unless the target chapter's `cbse_syllabus.rag_status` is literally `'ready'`.
  - Production had (and, per verification below, still has) **zero** `cbse_syllabus` rows at `rag_status='ready'`. Per PR #1394's own commit message, citing a CEO-reported production observation on 2026-07-27: 889 rows `partial`, 259 `missing`, 0 `ready`. *(Note: 889 + 259 = 1,148, which does not arithmetically reconcile with the ~761-row / 750-ready-chunks corpus figure quoted elsewhere in this repo's `CLAUDE.md`. Both are contemporaneous primary sources from the same repository; I could not reconcile the discrepancy from source alone — no live database query was available in this investigation. Flagging rather than picking one.)*
  - Why zero rows reach `'ready'`: `recompute_syllabus_status()` (`supabase/migrations/00000000000000_baseline_from_prod.sql:6380-6418`, read directly) computes `v_status := CASE WHEN v_chunks = 0 THEN 'missing' WHEN v_chunks < 50 OR v_questions < 40 THEN 'partial' ELSE 'ready' END` — confirming the exact `chunk_count >= 50 AND verified_question_count >= 40` predicate. The ~16,006 already-ingested NCERT chunks (per this repo's own `CLAUDE.md`, covering ~98.6% of chapters) satisfy the chunk half almost everywhere; the *verified-questions* half was never satisfied for any chapter. The corpus is not missing — the readiness signal never turns on.
  - PR #1394 (`2ad5ad37`, merged 2026-07-27) turned both flags OFF: `supabase/migrations/20260727120000_disable_ff_generation_agents.sql`. Its own comments (read in full) state this precisely and call out a load-bearing detail I independently confirmed by reading `packages/lib/src/supabase.ts`'s client-side `getFeatureFlags()`: it selects only `is_enabled` (not `rollout_percentage`), so a rollout-only kill (`rollout_percentage=0`) would have left the "Diagram"/"Lesson notes" pills **visible** in the UI while the server 404'd underneath — a worse state than today. `is_enabled=FALSE` was therefore required, not optional.

**Side-finding 1 (still open) — `ncert-solver` has had the identical dead end for months, undetected.** PR #1394 discloses this as a side-finding, not something it fixes: *"this gate is not new and not introduced by #1393 — `ncert-solver` is also `mode:'strict'` and has therefore been non-functional for months. `grounded_ai_traces` contains only `caller='foxy'` (soft mode skips the gate), which is why nobody noticed."* I confirmed in source that `ncert-solver/index.ts:438` sets `caller: 'ncert-solver'` and that the pipeline's `finalizeAbstain()` does write a trace row on abstain (with `grounded=false`, `abstain_reason`, and the caller field) — so this is not a structural inability to record ncert-solver traces, but an empirical finding about what the accumulated trace population actually looked like when examined. I could not independently re-verify the trace-population claim itself (no live database query available in this investigation) — reporting it as sourced to PR #1394's commit message, a primary but unverified-by-me source. Separately, I confirmed `quiz-generator` (the one quiz generator that exists on disk today) does **not** call the shared grounded-answer pipeline and is unaffected by this gate — only `ncert-solver` and the two now-disabled generation agents are.

**Side-finding 2 (fixed, in the same PR) — a Postgres function-overload bug had silently no-op'd an earlier RAG fix for ~20 days.** Migration `20260707010000` used `CREATE OR REPLACE FUNCTION` on `match_rag_chunks_ncert` with a renamed parameter (`p_min_quality` → `p_min_similarity`); in Postgres this creates a **second overload**, not a replacement. Both real call sites still sent `p_min_quality` (the old parameter name), so PostgREST kept resolving to the old, floor-less overload — the 2026-07-07 relevance-floor fix had never actually executed. PR #1394 fixed the caller side (`packages/lib/src/ai/retrieval/ncert-retriever.ts`, `supabase/functions/_shared/rag/retrieve.ts`, `supabase/functions/grounded-answer/retrieval.ts`, `apps/host/src/types/database.types.ts`) so calls resolve to the correct overload, and chose a measured floor of 0.22 (methodology recorded in the PR body). This is a genuinely fixed, closed sub-issue — included here for completeness since it shipped in the same PR, not because it is still open.

## Outstanding / NOT resolved

This is the section to read before treating this incident as closed. None of the following are done.

**(a) `ncert-solver`'s functional dead-end is still unfixed.** PR #1410 (2026-07-29) hardened its AI-safety posture only. It did not touch the coverage gate, `rag_status`, or `recompute_syllabus_status()`. I confirmed via a filename-timestamp scan of every migration after `20260727120000` (the disable migration) and a full-repo grep for `rag_status`, `verified_question_count`, and `recompute_syllabus_status` that **no migration since 2026-07-27 touches any of the three** — the only post-cutoff match at all is the disable migration itself. `ncert-solver` remains, today, in the same non-functional state PR #1394 found it in.

**(b) The RAG confidence signal is still uninformative on the live gate.** PR #1395's `confidence_v2` is shadow-only by construction (confirmed via REG-316's own test: a repo-wide scan finds zero production comparisons of `confidence_v2` to anything). The live `STRICT_CONFIDENCE_ABSTAIN_THRESHOLD = 0.75` (`supabase/functions/grounded-answer/config.ts:36`) still gates every `mode:'strict'` caller (`ncert-solver` and, if ever re-enabled, the two generation agents) against the old rank-based `confidence`. PR #1395's own "Next steps, not in this PR" is explicit that deriving a real threshold requires replaying ~1,353 historical queries (production traffic is only ~3 calls/day) and then CEO approval — none of which has happened.

**(c) Outcome Prediction has no UI and no rollout decision.** I confirmed via `grep` across `apps/host/src/app` that the only file referencing `predict/outcome` or `outcome_prediction` is the route itself (`apps/host/src/app/api/predict/outcome/route.ts`) — zero `.tsx` callers, same as Lesson/Content were before PR #1393, except nobody has since built its front door. Its flag `ff_outcome_prediction_v1` has never been enabled anywhere (confirmed: seeded OFF/0 in `20260724150000`, no later migration touches it). It is a fully tested, reviewed, "live" agent in the registry that delivers zero value to any student today, with no scheduled UI work and no explicit decision to hold it.

**(d) No safeguard yet prevents "flag reaches 100% same-day-as-seed" from recurring for a brand-new surface — and the specific fix for *this* incident's version of that gap is itself unfinished, uncommitted, and not confirmed working, as of this writing.** While investigating this incident I found the working tree of this exact repo checkout already contains an **uncommitted, in-progress** change addressing the "why nothing caught this" gap below: a new (currently untracked) migration `supabase/migrations/20260801120000_protected_feature_flags_genai_ecosystem_seed.sql`, plus uncommitted edits to `packages/lib/src/flags/protected-flags.ts` and two test files, registering 5 of the 6 GenAI-Phase flags (`ff_model_gateway_v1`, `ff_unified_memory_v1`, `ff_outcome_prediction_v1`, `ff_lesson_generation_v1`, `ff_content_generation_v1`) into `PROTECTED_FLAGS`/`EXPECTED_OFF_FLAGS` (deliberately excluding `ff_response_eval_v1`, with a stated rationale that it was a knowing, approved, non-implicated 100% rollout). **I did not create, edit, or commit any of this** — I only observed it and, at one point mid-investigation, re-ran the existing parity test (`apps/host/src/__tests__/api/super-admin/feature-flags-protected-guardrail.test.ts`) against the working tree as a read-only check. ## Why nothing caught this

Two distinct, structural gaps — both still open as of this writing except where item (d) above is (unverifiably, as of now) in flight.

**1. Unit tests mock the exact boundary where the failure lived.** I confirmed directly: `apps/host/src/__tests__/api/lesson/route.test.ts` and the equivalent `content/diagram/route.test.ts` both `vi.mock` the generator module itself (`@alfanumrik/lib/lesson/generate-lesson`, `@alfanumrik/lib/diagram/generate-diagram`) at the top of the file. The route tests are genuinely thorough about flag/auth/scope behavior (REG-313/REG-314 document dozens of assertions each), but by construction they replace the one function that actually calls the grounded pipeline with a fully-controllable stub — so no unit test in this repo could ever have exercised "does the real coverage gate, against real `cbse_syllabus` data, actually let a response through." Separately, no test type in this repo checks "does a `.tsx` file call this API route" — I searched for anything resembling a route-reachability or orphan-endpoint check and found none; the audit that caught Fault A was a manual, human-prompted investigation (triggered by the CEO's report), not an automated gate.

**2. None of the 6 new GenAI flags were ever added to the flag-governance registry.** I confirmed by reading `packages/lib/src/flags/protected-flags.ts` in full (as committed on `main`, before the in-progress uncommitted change described in Outstanding (d)) that none of `ff_response_eval_v1`, `ff_content_generation_v1`, `ff_lesson_generation_v1`, `ff_outcome_prediction_v1`, `ff_model_gateway_v1`, or `ff_unified_memory_v1` appears anywhere in `PROTECTED_FLAGS` or `EXPECTED_OFF_FLAGS`. This is not a guess — PR #1392's own commit message says it outright: *"None of the three flags is in `PROTECTED_FLAGS` / `EXPECTED_OFF_FLAGS` / the forced-OFF posture... that guardrail set is untouched."* And the `20260724150000` seed migration for `ff_outcome_prediction_v1` explicitly flags this as an unfinished follow-up in its own comments: *"Ops may need to add 'ff_outcome_prediction_v1' to EXPECTED_OFF_FLAGS... flagged to ops; not edited here."* Because the registry is opt-in per flag (by design, so unrelated flags aren't over-protected), and nobody opted these six in, the console confirm-gate, the DB-layer `BEFORE UPDATE` trigger, and the nightly/deploy-time posture canary — all of which are real and do work for every flag that *is* registered — had nothing to check. A flag outside the registry can go from freshly seeded to 100% production rollout in one console click with zero typed confirmation and zero canary alert, which is exactly what happened.

## Permanent safeguards

**Shipped (merged to `main`, verified in source):**
- REG-312 (`.claude/regression/02-foxy-ai.md`) — Outcome Prediction agent contract, read-only + IDOR-safe.
- REG-313 — Lesson Generation agent contract, abstain ladder + bilingual screen + flag-off no-op.
- REG-314 — Content Generation agent contract, dual safety gate (Mermaid injection + age/toxicity screen).
- REG-315 — Study Tools UI (`StudyToolsBar`) contract: flag-off DOM identity, fail-closed flag resolution, abstain-is-not-an-error rendering, client-side Mermaid re-validation.
- REG-316 (`.claude/regression/13-rag-cache.md`) — pins `confidence_v2` as shadow-only-and-never-compared, pins the `match_rag_chunks_ncert` overload count at exactly 2 (directly guards against a repeat of Side-finding 2).
- Both dead-end flags forced to `is_enabled=FALSE` (not merely `rollout_percentage=0`), which I confirmed is the behaviorally-correct choice given how the client-side flag reader works.
- `ncert-solver` AI-safety hardening (PR #1410).

**Proposed / in-progress, NOT landed (do not treat as shipped):**
- Making the `rag_status` coverage gate actually satisfiable — either getting real chapters to `'ready'`, or an assessment + ai-engineer-owned deliberate revision of the readiness predicate. PR #1394 itself lists this as deliberately deferred.
- Deriving and CEO-approving a real, relevance-based abstain threshold from `confidence_v2` and cutting the live gate over to it. Explicitly deferred per PR #1395.
- A functional (not just safety) fix for `ncert-solver`, or a decision to retire it.
- An Outcome Prediction UI, or an explicit decision to hold it.
- Registering the remaining GenAI flags in the flag-governance registry — **in progress, uncommitted, last observed with one test file still failing.** See Outstanding (d). Do not report this as closed without re-checking `git log` yourself.
- A structural check that a newly-registered "live" agent has at least one real caller before its flag can reach 100%. Not scoped anywhere I could find (no spec, runbook, or tracked follow-up item references this).

## Acceptance criteria for "never compromised again"

None of these are currently true. This incident should not be described as resolved until they are.

- [ ] At least one real production `cbse_syllabus` chapter reaches `rag_status='ready'` under the current predicate, OR the predicate itself is deliberately revised (assessment + ai-engineer decision) and re-verified against production data.
- [ ] A real `/api/lesson` and `/api/content/diagram` call, replayed against production data, returns a grounded (non-abstain) response — PR #1394's own stated re-enablement precondition.
- [ ] `ncert-solver` is either functionally fixed (not just safety-hardened) or explicitly retired by a documented decision.
- [ ] `confidence_v2` has been validated against a real historical-query replay, a threshold has been derived and CEO-approved, and the live strict-mode gate reads it instead of the rank-based `confidence`.
- [ ] Outcome Prediction has either a shipped UI consumer or an explicit, documented CEO/product decision to hold it indefinitely.
- [ ] All GenAI-ecosystem flags still relevant at that time are registered in `PROTECTED_FLAGS`/`EXPECTED_OFF_FLAGS`, the companion DB migration is merged to `main` (verify via `git log`, not a working-tree diff), and the full `feature-flags-protected-guardrail.test.ts` + `protected-flags-registry.test.ts` suite is green.
